# 교재 검토 관리

장·절·문단별 검토 상태, 수정 허용 범위와 검토 근거를 관리하는 로컬 도구이다. 원고는 읽기 전용으로 보여 주며, 상태와 작업 기록은 `review/state.json`에 저장한다. 교재 사이트에 포함하거나 배포하지 않는다.

개인 검토 상태·작업 이력·개별 보고서는 Git에서 제외한다. 공개 저장소에는 도구와 [초기 범위](scopes.json)만 포함한다. 로컬 상태가 없는 첫 실행에서는 이 범위의 모든 항목을 `unknown`으로 등록하며, 기존 상태가 있으면 초기 범위로 덮어쓰지 않는다.

## 실행

저장소의 `review.bat`를 직접 실행하면 브라우저에 관리 화면이 열린다. Python 3.10 이상과 Git이 필요하며 별도 Python 패키지는 필요 없다. `py`가 있으면 사용하고, 없으면 `python`을 사용한다.

```text
python scripts/review_server.py --open
```

기본 주소는 `http://127.0.0.1:8766/`이다. 포트를 바꾸려면 `--port 8767`을 덧붙인다. 실행한 창에서 Ctrl+C를 누르면 종료된다. 기존 교재 미리보기 서버와 별개이며, 사용자가 실행하기 전에는 관리 서버나 감시 프로세스가 시작되지 않는다. 관리 화면은 원격·공개 호스팅용이 아니다.

## 작업 순서

1. 왼쪽에서 대상을 선택하여 원고와 항목별 상태를 확인한다. `재검토 필요`는 변경 때문에 다시 확인할 항목이고 `검토 전`은 현재 사용할 검토 근거가 없는 항목이다. 숫자는 문장 수가 아니라 검토 항목 수이다.
2. 고칠 범위가 절보다 작으면 **범위 추가**로 문단·예제·문제를 등록한다. 원고에 별도 식별자를 넣지 않고 파일의 고유한 시작·끝 문구로 지정한다. 경계 문구 자체는 범위에서 제외된다. 장·절의 구성만 관리하는 범위에는 파일을 지정하지 않아도 된다.
3. 원고를 고치기 전에 **수정 작업 시작**에서 수정 목적, 고칠 범위, 함께 읽을 범위, 유지할 조건과 필요한 검토를 정한다. 시작 시점의 파일 상태가 저장되므로 기존 미커밋 변경은 이번 작업의 변경과 구별된다. 동시에 진행하는 수정 작업은 하나로 한정한다. 작업을 중단해야 하면 **미완료로 중단**을 사용한다. 미완료 검토와 변경 기록은 남으며 원고는 되돌리지 않는다.
4. 원고는 평소 사용하는 편집기에서 수정한다. 도구는 원고를 저장하거나 되돌리지 않는다. 수정 범위를 넓혀야 하면 새 부분을 고치기 전에 작업 창의 **범위 확대**로 기록한다.
5. **변경 확인**으로 상태를 갱신한다. 관리 화면으로 돌아올 때와 명령을 처리할 때도 확인한다. 등록 범위의 내용 변경은 해당 항목과 명시적으로 연결된 의존 항목을 `dirty`로 만든다. 의미·선수 관계·전파 경계는 검토자가 판단하여 **문제 기록**이나 **연결**로 보충한다.
6. **검토 시작**으로 검토할 버전을 잡고 내용을 확인한 뒤 근거와 검토자를 기록한다. 근거를 입력하는 동안 내용·문맥·의존 입력이 바뀌면 완료를 거부한다. 적용되지 않는 항목은 구체적인 이유와 함께 **해당 없음**으로 판정한다. 실패했거나 실행하지 못한 검사를 이 판정으로 덮지 않는다.
7. 필요한 항목을 마쳤으면 수정 작업 창에서 실제 변경 범위를 확인하고, 상위 범위로 검토를 더 넓히지 않아도 되는 근거를 적어 완료한다. 미검토 항목이나 범위 밖의 변경이 남아 있으면 완료되지 않는다. 이때 다른 사람이 고친 내용을 자동으로 되돌리지 말고 변경의 출처를 먼저 확인한다.

작은 범위를 하위에 등록하면 그 부분의 변경은 하위 항목이 추적하며, 부모는 그 밖의 본문을 추적한다. 부모의 `contains_dirty`는 하위에 미완료 항목이 있다는 집계이다. 부모 자체의 검토를 무효화해야 하는 경우에는 해당 항목을 별도로 연결한다. 상위 검토를 통과해도 하위의 증명·문제 검사가 완료되지는 않는다.

경계 문구가 없어지거나 중복되면 그 범위를 완료할 수 없다. **경계 수정**에서 새 위치와 이유를 기록하면 재검토 대상으로 남는다. 이 조작은 진행 중인 작업의 수정 허용 범위를 바꾸지 않는다. 제목·경계 자체를 수정할 계획이라면 먼저 그것을 포함하는 바깥 범위를 허용해야 한다.

## 자동으로 판단하지 않는 것

기준 문서(`REVIEW_PROCESS.md`, `STYLE.md`, `AGENTS.md`, `REVIEW_TEMPLATE.md`)가 바뀌거나 삭제되면 전역 재검토 표시가 켜지고 등록 항목이 모두 `dirty`가 된다. 기준 버전이 없는 이전 완료 기록도 처음 연결할 때 재확인한다. 관리 화면 상단에는 새 기준의 판정이 남은 항목 수가 나타나며, 각 완료 기록에는 검토 기준의 버전이 함께 저장된다. 변경 전의 검토표로는 완료할 수 없다.

새 기준으로 모든 대상의 판단을 기록하면 전역 표시가 사라진다. 이 표시는 국소 원고 수정의 `dirty`와 구별한다. 이전 실행 로그의 재사용 여부와 새 기준이 요구하는 독해·예제 검토는 `REVIEW_PROCESS.md`에 따라 판단하며, 버튼으로 전역 표시만 강제로 지우지는 않는다.

- 도구는 문장의 뜻, 학습 흐름, 문제의 풀이 가능성을 판정하지 않는다. [검토 절차](../REVIEW_PROCESS.md)의 최소 검토 범위를 사람이 먼저 정한다. 작업 시작 시 수정 대상의 등록된 검토 항목과 바로 위의 경계·구성 항목을 포함하는 것은 최소한의 누락 방지 장치이다.
- 초기 상태에는 네 장의 절과 부록만 등록했다. 과거 기록을 일괄 통과 처리하지 않았고, 절 사이의 의미상 의존 관계도 자동 추정하지 않았다. 새 내용과 사용처를 확인하면서 더 작은 범위와 필요한 의존 관계를 추가한다. 관계가 더 이상 성립하지 않으면 이유를 기록하여 연결을 해제하며, 그 대상의 재검토 상태는 유지한다.
- 변경 감지는 현재 저장된 파일을 대상으로 한다. 편집기의 미저장 내용이나 두 번의 확인 사이에 수정했다가 완전히 되돌린 내용은 추적하지 않는다. 이동·외부 환경 변화로 검토 근거가 달라졌다면 직접 원인을 남긴다.
- 수정 범위 검사는 Git이 추적하거나 무시하지 않은 파일을 대상으로 한다. 빌드 출력·개인 풀이·`tmp/` 등 무시된 파일까지 감시하지 않는다. 외부 편집기의 쓰기를 잠그는 기능도 아니다. 작업 시작·완료 시 전체 차이를 함께 확인한다.
- 같은 내용을 다른 곳으로 옮겼다면 출발·도착 문맥을 각각 검토한다. 본문이 같은지 확인하는 해시만으로 전파를 멈추지 않는다.

## 저장 형식

`review/state.json`이 현재 상태의 원본이다. [REVIEW_STATE.md](../REVIEW_STATE.md)는 이 도구로 들어오는 안내이며 별도 상태 장부로 갱신하지 않는다.

| 자료 | 저장 내용 |
|---|---|
| `units` | 범위의 이름·층위·부모·파일 경계, 항목별 상태·세대·변경 원인·검토 근거 |
| `dependencies` | 어떤 검토가 어느 검토에 의존하는지와 그 이유 |
| `tasks` | 수정 목적, 수정·참조 범위, 유지 조건, 필요한 검토, 범위 확대와 완료 기록 |
| `history` | 상태 변경과 검토 완료의 시각·원인·근거 |
| `revision` | 동시에 열린 화면이 서로의 변경을 덮지 않도록 확인하는 저장 버전 |

`unknown`, `dirty`, `clean`과 근거를 붙인 제외 판정 `not_applicable`을 구별한다. 새 변경은 완료·제외 판정을 다시 `dirty`로 만든다. 동일한 항목의 여러 변경 원인은 현재 검토에 모두 포함되어야 해제된다. 의존 관계는 순환할 수 없으며, 의존 항목의 검토가 끝나기 전에는 그 결과를 사용하는 항목을 완료할 수 없다.

`review/local/`에는 시작 시점의 파일 해시·허용 범위가 있는 파일의 내용, 직전 상태 백업과 저장 잠금이 남는다. Git에는 포함하지 않는다. 작업의 시작 기준이 없는 다른 컴퓨터에서는 그 작업을 완료할 수 없다. 기준 파일을 삭제하거나 현재 상태로 다시 만들어 기존 범위 밖의 수정을 숨기지 않는다.

프로세스가 비정상 종료되어 저장 잠금이 남았다면 모든 관리 도구가 종료되었음을 확인한 뒤 `review/local/write.lock`만 제거한다. `state.previous.json`은 직전 저장 상태의 복구 자료이다. 상태를 수동 복구할 때는 현재 파일을 먼저 보존하고 원고와 대조한다.

## 명령줄

웹 화면과 명령줄은 `scripts/review_state.py`의 같은 상태 전이를 사용한다.

```text
python scripts/review_state.py status
python scripts/review_state.py dirty --input tmp/review-command.json
```

명령 인수는 UTF-8 JSON 파일로 전달한다. 예를 들어 한 설명에서 문맥 검토가 필요함을 기록할 때는 다음과 같이 쓴다. 실제 범위 ID는 `status`의 `units`에서 확인한다.

```json
{
  "checks": ["proof-01/context"],
  "reason": "앞 문단에서 도입한 명제와 이 예제의 관계를 확인해야 함"
}
```

| 명령 | 주요 인수 |
|---|---|
| `status`, `scan` | 현재 파일과 대조한 상태 조회 |
| `register` | `id`, `title`, `level`, `parent`, `sources`, `checks` |
| `relocate` | `unit`, `sources`, `reason` |
| `dirty` | `checks`, `reason` |
| `link`, `unlink` | `from`, `to`, `reason` (항목 ID는 `범위/검토항목`) |
| `source` | `unit` |
| `prepare` | `check`; 반환된 `result`가 검토 버전표 |
| `accept` | `check`, `ticket` (버전표), `evidence`, `reviewer`, 선택적 `verdict` |
| `begin` | `title`, `reason`, `invariants`, `edit_units`, `read_units`, `required` |
| `expand` | `edit_units`, `reason` |
| `finish` | `boundary` |
| `stop` | `reason` (미완료 상태 보존) |

`sources`는 `[{"path":"AlgebraBook/Proof.lean", "after":"고유한 시작 문구", "before":"고유한 끝 문구"}]` 형식이다. 경계를 생략하면 파일 전체이다. 경로는 이 저장소 기준이며 저장소 밖·Git 내부·로컬 검토 스냅샷은 원고 범위로 등록할 수 없다. 다른 저장소를 관리할 때는 그 저장소에 별도의 `review/state.json`을 두고 `--root`를 지정한다.

`--revision 숫자`를 지정하면 읽은 버전과 저장 버전이 다를 때 쓰기를 거부한다. 웹의 변경 요청은 항상 이 확인을 사용한다. `prepare` 이후 내용을 검토하고 반환된 버전표로 `accept`를 호출해야 하며, 명령줄에서도 단순히 상태 문자열만 바꾸지 않는다.

## 검사

```text
python tests/ReviewState.Tests.py
node tests/ReviewWeb.Tests.cjs
```

두 검사 모두 임시 Git 저장소를 사용하고 리스너를 열지 않는다. 두 번째 검사는 Playwright와 Chromium이 필요하며 브라우저 요청을 실제 상태 관리 코드로 연결해 화면 조작을 검사한다. 필요하면 `PYTHON`·`CHROME_PATH`로 실행 경로를 지정한다. 실제 HTTP의 로컬 주소·인증 검사는 첫 번째 검사에서 포트를 열지 않고 요청 처리기를 직접 호출한다.
